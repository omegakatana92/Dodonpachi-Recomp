# Architecture

## Why static translation

An emulator interprets each 68000 instruction at run time. This project instead runs the
game's own algorithms as C:

1. `tools/core/m68000/analysis.py` finds the code reachable from the 68000 exception vectors
   and from `symbols.txt`. It follows direct and computed branches, jumps and calls and reads
   the handler tables those reach.
2. `tools/core/m68000/translate.py` lifts every instruction to an IR and writes one C
   function per game function. The C manipulates the 68000 register file and calls the board
   through the bus helpers in `runtime/include/m68000/ops.h`.
3. The generated C is compiled together with this repository's board runtime. No instruction
   fetch, decode, or 68000 interpreter remains in the shipped binary.

The board runtime is the only emulation-like layer: it models the memory-mapped registers,
video chips, inputs and sound chip behavior. That is the hardware `ddonpach` ran on, not a
CPU emulator.

## Layers

### Generated program (`build/generated/`)

- `program.h`: prototypes plus `PROGRAM_FRAME_WAIT`.
- `program_NN.c`: the translated functions.
- `entries.c`: `m68k_code_entries[]`, the address-to-function table used by computed jumps,
  interrupts and the reset vector.

Generated output is derived from the user's ROM and is git-ignored. It is never distributed.

### 68000 runtime (`runtime/src/m68000.c`, `runtime/include/m68000/`)

Provides the contract the generated C expects:

- `m68k_cpu cpu` with D0-D7, A0-A7, the other stack pointer, the system byte and X/N/Z/V/C.
- `m68k_read_sr` / `m68k_write_sr`, including the supervisor/user stack swap.
- `m68k_call`, `m68k_jump`, `m68k_calls_push`, `m68k_returned_to`.
- `m68k_exception`, `m68k_take_interrupts`, `m68k_stop`, `m68k_reset_devices`.
- `program_frame_wait`, called at the game's idle instruction (`0x0571B2`), which advances
  the board to the next VBLANK and delivers pending interrupts.
- `mem_read8/16/32`, `mem_write8/16/32` in `ops.h`; these forward to `cave_read16` and
  `cave_write16` with MAME's byte-lane mask convention.

### Board (`runtime/src/machine.c`, `runtime/include/cave/machine.h`)

`cave_machine` owns:

- the 1 MiB program ROM supplied by the player at run time;
- 64 KiB work RAM;
- 64 KiB sprite RAM;
- layer 0 (32 KiB), layer 1 (32 KiB), layer 2 (16 KiB, mirrored) tile RAM;
- 64 KiB palette;
- 128 bytes of video registers and the IRQ-cause latch;
- layer control registers;
- inputs, EEPROM state and coin counters;
- the YMZ280B register file and sample ROM.

The 68000 bus is 16 bits with a 24-bit address. Byte lanes use `mem_mask` values `0xFF00`
(even byte) and `0x00FF` (odd byte), matching MAME's convention. Addresses outside a device
read as zero and writes are logged in debug builds.

### Video (`runtime/src/video.c`)

The visible resolution is 320x240, rotated 270 degrees for display. Three 038-style tile
layers and the NEC 013 sprite generator are drawn in priority order. The first milestone
only needs a stable frame and a non-blank picture; exact per-pixel comparison against MAME is
a later accuracy milestone.

### Audio (`runtime/src/ymz280b.c`)

The YMZ280B is implemented from its register interface: key-on/off, sample start/end
addresses, pitch, level, pan, loop and ADPCM decoding. It reads the 4 MiB sample ROM supplied
by the player. Until audio is implemented, writes are accepted and reads return a sane status
so the boot does not stall.

### Ports (`ports/headless`, `ports/sdl2`)

- Headless: deterministic frame loop, hash log, exit code on a missing translated entry or an
  invalid bus access. This is the CI gate.
- SDL2: creates the window, texture, input mapping and audio device; it calls the same
  `program_reset` / `program_run` entry points as headless.

## Boot and frame model

The board boots at the 68000 reset vector: SSP `0x110000`, PC `0x0052EA`. The reset routine
initialises hardware, runs the ROM checksum, and eventually jumps to the main loop at
`0x000A80`. The main loop's per-frame synchronisation is the routine at `0x05718E`; its idle
instruction is `0x0571B2` (`tst.w $100F44`). The VBLANK handler sets `$100F44`, and the board
raises IRQ level 1 at VBLANK.

In the translated program instructions take no time. `program_frame_wait()` is called at
`0x0571B2`; when the board is at the end of a frame it advances to the next VBLANK, runs the
frame's events, and lets `m68k_take_interrupts()` run the level-1 autovector handler. This
mirrors `kref --timing frames` from the upstream toolchain.

## Determinism

The game's random numbers are generated by its own code from RAM state; no host RNG is used.
Headless runs are therefore reproducible for a fixed ROM, input script and frame count.

## Runtime implementation notes

- `runtime/include/m68000/ops.h` defines the ALU helpers the generated C calls (shifts,
  carry/overflow, DIVU/DIVS, ABCD/SBCD, `mem_read*`/`mem_write*`) with the same results as
  `tools/core/m68000/interpreter.py`.
- `runtime/src/m68000.c` holds the architectural state, exception/interrupt frames, the
  shadow call stack, and computed calls/jumps. It contains no instruction decoder.
- `runtime/src/machine.c` decodes the bus, tracks unmapped accesses, drives the palette,
  layer and video registers, inputs, the 93C46 and the VBLANK. The EEPROM latch is on the
  high byte of the 16-bit write at `e00000`, matching MAME's `eeprom_w(u8)` call.
- `runtime/src/video.c` renders the 038 layers and 013 sprites; `--png` saves a
  development snapshot.
- `runtime/src/rom.c` reads the player's `.zip` with miniz and verifies every file by CRC32
  and SHA-1. Sprite data is word-swapped as MAME's `ROM_LOAD16_WORD_SWAP` loads it.

## Analysis seeding

The static analysis cannot follow every computed dispatch. The game-specific tools write
address-only symbol blocks (never data) into `symbols.txt`:

- `tools/seed_symbols.py`: every `jmp` instruction (MAME handler tables of trampolines).
- `tools/seed_tables.py`: the object table at `015A8A` (`+4` handlers and the word-prefixed
  `+0` code blocks).
- `tools/seed_dispatch.py`: PC-relative `jmp/jsr (d16,PC,Dn.w)` tables.
- `tools/seed_trace.py`: optional gaps from a MAME debugger execution trace; development
  reference only, never linked or shipped.

`tools/extract_program.py` writes the interleaved program image to `build/program.bin` for
the development scripts (git-ignored).

`tools/core/m68000/translate.py` has a local fix for functions that push a return address
with `PEA` and continue there after the helper returns; the fix should be upstreamed and the
core pinned as a submodule.

## Security and distribution

The executable opens the user's ZIP, verifies every file by CRC32 and SHA-1, extracts only
known region names, and loads the program/sample/graphics regions into private buffers. It
does not execute data from the ZIP and does not ship any ROM bytes. Release archives contain
only binaries, licenses and documentation.
